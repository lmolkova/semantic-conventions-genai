# Semantic Conventions for GenAI turns

**Status**: [Development][DocumentStatus]

<!-- toc -->

<!-- tocstop -->

A **turn** is the handling of one request to an agentic system: everything the system does
between receiving a request and producing its final response.

Callers do not know, and SHOULD NOT need to know, how the system is built internally. A turn may
be handled by a single agent, by a workflow coordinating several agents, or by arbitrary
application code. Refactoring between these shapes does not change the
turn: its duration, its identity, and its telemetry stay the same. This is what makes
`handle_turn` usable for dashboards and alerts that must survive changes to the internals of the
agentic system, whether those internals belong to the application, a framework, or a hosted
agent behind an API.

## How turns relate to other operations

The turn is the outermost GenAI operation in a process. Everything the request fans out into -
agent and workflow invocations, inference, tool calls, retrieval, memory operations - is nested
under it, including handoffs between agents:

```
handle_turn support_assistant
├── invoke_agent triage
│   ├── chat
│   └── execute_tool lookup_order
└── invoke_agent refunds          # handoff, sibling of triage
    └── chat
```

The turn does not replace the operations underneath it. When a single agent handles the request
end to end, both spans are still reported and have the same duration:

```
handle_turn support_assistant
└── invoke_agent support_assistant
    └── chat
```

This redundancy is intentional. It is what lets a consumer query system-level latency, errors,
and cost the same way regardless of whether the system is one agent, a graph, or a handoff
chain - and keeps those queries working when the implementation changes between them. Agent
invocations remain separately observable through `invoke_agent` spans and
`gen_ai.invoke_agent.duration` metric; see [Agent spans](gen-ai-agent-spans.md).

Operations nested under the turn carry `gen_ai.main_agent.name`, so their spans and metrics can
be attributed to the system that produced them without traversing traces.

Represents handling of one request to the agentic system.

The `gen_ai.operation.name` SHOULD be `handle_turn`.

The turn span is the outermost GenAI operation in a process. It covers everything done
to handle a single request to the agentic system: agent invocations, workflows,
inference, tool calls, retrieval, and memory operations, including handoffs between
several agents.

Instrumentations SHOULD report a turn span when they can reliably bound a request to the
agentic system and no other GenAI turn operation is present in the context.

Operations internal to handling a request are not turns and SHOULD NOT be reported as such.
This includes inference, tool calls, retrieval, and memory operations, as well as invocations
of sub-agents and nested workflows, regardless of whether the instrumentation that reports
them can observe the enclosing turn.

**Span kind** is always `INTERNAL`. The turn is a logical boundary, not a transport one.
When the agentic system is reached over a network protocol, the protocol instrumentation
reports the `SERVER` span and the turn span is nested under it.

The entity that owns the turn may be an agent, a workflow, or an application-specific
entry point. `gen_ai.main_agent.name` identifies it in all cases; `gen_ai.agent.name` and
`gen_ai.workflow.name` describe what it is when applicable.

The turn span is reported independently of what handles the request, including when a
single agent handles it end to end. In that case the `invoke_agent` span for that agent
is reported as a child of the turn span and the two have the same duration.

**Span name** SHOULD be `handle_turn {gen_ai.main_agent.name}` if `gen_ai.main_agent.name` is readily available. When it is not available, it SHOULD be `handle_turn`.

**Span status** SHOULD follow the [Recording Errors](https://github.com/open-telemetry/semantic-conventions/blob/v1.44.0/docs/general/recording-errors.md) document.

**[1] `gen_ai.operation.name`:** If one of the predefined values applies, but specific system uses a different name it's RECOMMENDED to document it in the semantic conventions for specific GenAI system and use system-specific name in the instrumentation. If a different name is not documented, instrumentation libraries SHOULD use applicable predefined value.

**[2] `error.type`:** The `error.type` SHOULD match the error code returned by the Generative AI provider or the client library,
the canonical name of exception that occurred, or another low-cardinality error identifier.
Instrumentations SHOULD document the list of errors they report.

**[3] `gen_ai.agent.name`:** When the turn is owned by an agent and the name is available.

**[4] `gen_ai.conversation.id`:** If and only if the instrumented library has one readily available, or the user application provides one through OpenTelemetry context or library-specific mechanisms.

**[5] `gen_ai.conversation.id`:** Instrumentations SHOULD populate conversation id when they have an identifier
for the conversation readily available for a given operation, for example:

- when the client framework being instrumented manages conversation history
(see [LlamaIndex chat store](https://docs.llamaindex.ai/en/stable/module_guides/storing/chat_stores/),
[LangChain `session_id`](https://reference.langchain.com/python/langchain-core/runnables/history/RunnableWithMessageHistory),
and [Google ADK sessions](https://adk.dev/sessions/session))
- when instrumenting GenAI client libraries that maintain a conversation on the backend
(see [AWS Bedrock agent sessions](https://docs.aws.amazon.com/bedrock/latest/userguide/agents-session-state.html),
[OpenAI Assistant threads](https://platform.openai.com/docs/api-reference/threads))

When no identifier for the conversation is available, instrumentations SHOULD NOT
populate conversation id. For example, a new UUID, a trace identifier, or a hash
of request content SHOULD NOT be used as a fallback value.

Application developers that manage conversation history MAY add conversation id to GenAI and other
spans or logs using custom span or log record processors or hooks provided by instrumentation
libraries.

**[6] `gen_ai.main_agent.name`:** The main agent is what the caller of the agentic system talks to, regardless of
whether it is implemented as a single agent, a workflow, or a custom orchestration.

Instrumentations SHOULD set this attribute on the `handle_turn` span and SHOULD propagate it
to GenAI operations nested under the turn within the same process, so that spans and
metrics can be attributed to the system that produced them.

Applications that run a single main agent MAY describe it with the `gen_ai.main_agent`
entity, which carries the same name at the process level. When both are present, the value
reported by the instrumentation and the one configured by the application are expected to
match.

Instrumentations often cannot determine the main agent name. In those cases it is expected
to be available through the entity attributes instead.

This attribute MUST have low cardinality.

**[7] `gen_ai.workflow.name`:** When the turn is owned by a workflow and the name is available.

**[8] `gen_ai.workflow.name`:** The workflow name is usually a static, application-unique identifier defined
in a framework-specific way.

For example, it can be the name of the first chain in LangChain,
the name of the crew in CrewAI, or the entry point agent in ADK or
OpenAI Agents when no explicit workflow name is provided.

This attribute MUST have low cardinality. It is NOT RECOMMENDED to use
instrumentation-time constants or names of types representing the workflow,
such as "StateGraph". When no meaningful, low-cardinality workflow name is
available for a given framework, this attribute MUST NOT be captured by default.

Semantic conventions for individual Generative AI frameworks SHOULD document
what `gen_ai.workflow.name` means in the context of that framework.

**[9] `gen_ai.input.messages`:** Messages MUST be provided in the order they were sent to the model.
Instrumentations MAY provide a way for users to filter or truncate
input messages.

> [!Warning]
> This attribute is likely to contain sensitive information including user/PII data.

See [Recording content on attributes](/docs/gen-ai/gen-ai-spans.md#recording-content-on-attributes)
section for more details.

Instrumentations MUST follow [JSON schema](/model/gen-ai/gen-ai-input-messages.json).

When the attribute is recorded on events, it MUST be recorded in structured form. When recorded on spans, it MAY be recorded as a JSON string if structured format is not supported and SHOULD be recorded in structured form otherwise.

**[10] `gen_ai.output.messages`:** Each message represents a single output choice/candidate generated by
the model. Each message corresponds to exactly one generation
(choice/candidate) and vice versa - one choice cannot be split across
multiple messages or one message cannot contain parts from multiple choices.

Instrumentations MAY provide a way for users to filter or truncate
output messages.

> [!Warning]
> This attribute is likely to contain sensitive information including user/PII data.

See [Recording content on attributes](/docs/gen-ai/gen-ai-spans.md#recording-content-on-attributes)
section for more details.

Instrumentations MUST follow [JSON schema](/model/gen-ai/gen-ai-output-messages.json).

When the attribute is recorded on events, it MUST be recorded in structured form. When recorded on spans, it MAY be recorded as a JSON string if structured format is not supported and SHOULD be recorded in structured form otherwise.

* [`gen_ai.main_agent.name`](/docs/registry/attributes/gen-ai.md)
* [`gen_ai.operation.name`](/docs/registry/attributes/gen-ai.md)

## Events

Turns do not define events of their own. Turn inputs and outputs are recorded as
`gen_ai.input.messages` and `gen_ai.output.messages` attributes on the turn span when opted in;
nested operations report their own details, see [GenAI events](gen-ai-events.md).
