# Contributing

Welcome to the OpenTelemetry GenAI Semantic Conventions repository!

New to OpenTelemetry? Read the
[New Contributor Guide](https://github.com/open-telemetry/community/blob/main/guides/contributor/README.md)
first — it covers the CLA, Code of Conduct, and other prerequisites.

## Prerequisites

- [Docker](https://docs.docker.com/get-docker/) (or a compatible runtime
  such as Podman aliased as `docker`) — `make` runs Weaver via the
  `otel/weaver` container image.
- [GNU Make](https://www.gnu.org/software/make/) — pre-installed on macOS
  and Linux. On Windows, use [WSL](https://learn.microsoft.com/windows/wsl/install)
  or install via [Chocolatey](https://chocolatey.org/) (`choco install make`)
  or [Scoop](https://scoop.sh/) (`scoop install make`).

## Code structure

```text
├── model
│   └── <namespace>/                  # e.g. gen-ai, mcp, openai
│       ├── registry.yaml             # attribute definitions
│       └── spans.yaml, metrics.yaml, events.yaml, entities.yaml
├── docs
│   ├── README.md                     # entry point
│   ├── <namespace>/                  # gen-ai, mcp, a2a, openai, anthropic, azure, aws
│   │   ├── README.md                 # namespace overview (gen-ai uses docs/README.md)
│   │   ├── <op>.md                   # operation docs, e.g. client-inference.md
│   │   └── registry/                 # generated, do not edit
│   │       ├── README.md             # index of signals, attributes, deprecated items
│   │       └── spans|metrics|events|entities/
│   │           ├── <id>.md           # one page per signal
│   │           └── refinement.<id>.md
│   └── gen-ai/non-normative/         # examples and design notes
└── templates/registry/markdown/      # Weaver templates and jq helpers (jq/docs.jq)
```

All attributes must be defined in `registry.yaml` files under the matching
namespace folder in `model/`.

> [!IMPORTANT]
> Everything under `docs/` except `docs/<namespace>/registry/` is hand-written.
> Hand-written docs MAY embed generated index tables (see [Snippets](#snippets)),
> but SHOULD link to the full signal definitions under `registry/` instead of
> re-rendering them.

### What goes where

- Put everything that applies to a single signal or attribute in YAML
  (`brief`, `note`, requirement levels, annotations). Use hand-written docs
  only for guidance that spans several signals, and for examples.
- `docs/<namespace>/registry/` and the content between
  `<!-- weaver ... -->` and `<!-- endweaver -->` in hand-written docs are
  generated by `make generate-all`. Don't edit them by hand.

### Annotations used by the docs

- `annotations.docs.operation: <operation>` links a signal to an operation:
  it shows up in that operation's index tables and its page links back to the
  operation docs. Refinements inherit it. Every signal gets a registry page
  with or without it.
- `annotations.code_generation.explicit_bucket_boundaries` sets the advisory
  histogram buckets shown on the metric page.
- `annotations.markdown.omit: true` on an attribute reference hides it from
  the generated attribute table.

### Snippets

Hand-written docs embed generated index tables with helpers from
`templates/registry/markdown/jq/docs.jq`:

```html
<!-- weaver operation_index_table("gen_ai.client.inference"; "spans") -->
<!-- endweaver -->
<!-- weaver namespace_index_table("openai"; "metrics") -->
<!-- endweaver -->
```

Add new helpers to `jq/docs.jq` instead of writing inline jq in markdown.

- New operation: annotate its signals and create `docs/<namespace>/<op>.md`
  with one index table per signal type. Link it from `docs/README.md`.
- New namespace: its registry is generated automatically. Add
  `docs/<namespace>/README.md` with `namespace_index_table` snippets and link
  it from `docs/README.md`.

## Making a change

### 1. Modify the YAML model

Refer to the
[Semantic Convention YAML Language](https://github.com/open-telemetry/weaver/blob/main/schemas/semconv-syntax.md)
to learn about the YAML file syntax.

### 2. Regenerate the docs

After updating the YAML, run:

```bash
make generate-all
```

This regenerates the registry pages under `docs/<namespace>/registry/`,
refreshes the generated tables embedded in hand-written docs and regenerates
the status reports.

### 3. Validate

Run the shared policy checks:

```bash
make check-policies
```

This validates the model against shared OpenTelemetry policies covering
naming conventions, attribute type rules, stability requirements, and
backwards compatibility.

Run the link checks (optional, requires [mise](https://mise.jdx.dev/)):

```bash
mise run links
```

### 4. Update reference scenarios

Changes under `model/` or `docs/` typically require updating the
reference scenarios under `reference/` to demonstrate that the proposed
updates are capturable. See [reference/CONTRIBUTING.md](reference/CONTRIBUTING.md)
and the [reference skill](.github/skills/reference/SKILL.md).

### 5. Update the changelog

Add a Towncrier fragment under [changelog.d/](changelog.d/) for any change to
the conventions that a consumer would care about. Editorial changes - typos,
pure rewording, and repo tooling - don't need an entry.

Use a filename of `<pr-number>.<type>.md` once the pull request number is
known, or `+.<type>.md` before then. Add a numeric counter before `.md` when
one pull request needs multiple fragments of the same type. See
[changelog.d/README.md](changelog.d/README.md) for the supported types.

## Keep PRs small

Small, focused PRs are much easier to review, and therefore much more
likely to land quickly. Consider phasing larger changes across multiple PRs
where possible.

If a PR review surfaces contentious or difficult points, consider splitting
those into follow-up PRs so the uncontroversial parts can land and each of the
harder points gets its own focused discussion and review.

For more information about the approver role, see the [community repository](https://github.com/open-telemetry/community/blob/main/guides/contributor/membership.md#approver).

Approvers assign themselves to non-editorial PRs
to signal that they will drive the review. A PR can have multiple
approvers assigned, and that is highly encouraged for medium and high
complexity PRs.

Over a rolling 3-month window, an approver is expected to sign up for and
drive the review of at least 3 non-editorial PRs.
"Driving the review" means staying engaged with the PR through to its
merge or close: providing timely initial reviews and follow-up feedback,
requesting changes, asking design questions, and re-reviewing revisions
promptly until the PR lands or is rejected.
